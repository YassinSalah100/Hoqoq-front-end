# Hoqooq Backend API Contract (live, verified 2026-07-22)

Generated by pulling `GET /api/docs-json` directly off the running backend
(`hoqoq backend/Hoqooq`, commit `d1ae7a6`) and cross-checking against source
where the spec was silent. This supersedes `API_ENDPOINTS.md` — that file only
listed URLs; this one has the actual request/response shapes.

Base URL: `http://localhost:3000/api` (Swagger UI: `http://localhost:3000/api/docs`)

## What changed since the last frontend integration pass

- **Signup/login 500 (`EntityPropertyNotFoundError`) is fixed.** Both work end-to-end now.
- **RBAC is real and enforced**, but the dev DB needs seeding for any of it to work:
  run `npm run seed` in the backend repo once. It creates the permission dictionary,
  6 roles, and the `admin@hoqooq.local` / `HoqooqAdmin2024!` account.
- **Signup auto-assigns a role now.** `userType: LAWYER` → user gets the `lawyer` role
  with full firm permissions (see Roles below). `userType: CLIENT` → `tenant: null`,
  no firm role.
- A full **Tenants module** landed (`/api/tenants/my-firm`) — this is the real home for
  "firm info" settings, not the generic `/api/settings` key-value store.
- **Reviews** and **Consultations** modules exist now with real DTOs (richer than the
  placeholder shape the frontend originally guessed).

## Fixed during this integration pass (backend source, not yet committed)

### Critical: two endpoints leaked data across tenants

Found by signing up a **second, independent** firm account and noticing its
dashboard showed the *first* firm's cases/tasks/activity. Root cause: neither
endpoint filtered by `tenantId` at all — they queried across every tenant in
the database.

1. **`GET /api/dashboard` ignored tenant scoping entirely** (`dashboard.service.ts`
   `getSummary()`). Every `count()`/`find()` call — total/active cases, pending
   tasks, upcoming hearings, invoices, recent activity — ran with no `where`
   clause, so every firm saw every other firm's aggregate numbers and activity
   feed. Fixed: `getSummary(userId, tenantId)` now filters every query by
   `tenantId`, and returns an all-zero summary if `tenantId` is falsy (e.g. a
   client account) instead of leaking global data.
2. **`GET /api/reports/export/cases` and `/export/clients` had the same bug**
   (`reports.service.ts`). `exportCasesCsv()`/`exportClientsCsv()` fetched every
   case/client in the database with no tenant filter. Fixed: both now take
   `tenantId` (cases) or `userId, tenantId` (clients — see note below) and scope
   accordingly; both controller methods now pass `user.tenantId`/`user.id`.
   - `Client` has **no `tenantId` column** — it's linked to a tenant only
     indirectly through `cases`/`consultations` that reference it. There's
     already a correctly-scoped query for this on `ClientRepository.findScopedForTenant()`
     (used by `ClientsService.findAll()`) — the export fix reuses it rather than
     adding a `where: { tenantId }` that would crash the same way the case-notes
     bug did (filtering on a column that doesn't exist).

**Not fixed, flagging instead — still a gap**: `ClientsService.findOne(id)` has
no tenant/ownership check at all; any authenticated user who knows (or guesses)
a client UUID can fetch that client's full record regardless of tenant. Fixing
it properly needs the same EXISTS-subquery scoping as `findScopedForTenant`,
applied to a single-row lookup — didn't want to guess at that without being able
to fully test it. Same is likely true for other `findOne(id)` methods across
modules that don't take a `tenantId` — worth an audit.

### `POST /api/clients` created invisible clients

Found by actually creating a client through the frontend's new "إضافة موكل" form
and watching it vanish — `GET /api/clients` never showed it again, even to the
user who'd just created it. Root cause: `ClientsController.create()` never took
`@CurrentUser()`, so `ClientsService.create()` never set `createdBy`. Since
`Client` has no `tenantId` column (see above), a freshly created client is only
visible via `findScopedForTenant`'s `createdBy = userId` clause or via a
case/consultation that references it — a brand-new client has neither, so it's
orphaned and invisible until some later action links it to something. Fixed:
`create()` now takes the current user's id and sets `createdBy`, matching what
`createClientProfile()` already did correctly.

### Frontend: sidebar was leaking the admin-only "المستخدمون" (Users) nav item

Unrelated to the backend, but worth noting: giving the `lawyer` role's sidebar
config `sidebarItems: 'all'` meant it also matched the newly-added `'users'` key,
so firm lawyers saw a "Users" link they have no `users.*` permission to actually
use (would 403). Fixed in `src/data/auth.js` — `canSeeSidebarItem()` now treats
`'users'` as admin-only regardless of any role's `'all'` wildcard.

### Case notes / assignments (found earlier in this integration)

Two more real bugs were found by actually clicking through the frontend against a
seeded, populated tenant and were fixed directly in
`hoqoq backend/Hoqooq/src/modules/cases/`:

3. **`GET /api/cases/:id` 500'd (`EntityPropertyNotFoundError`).** `CaseNote`'s
   `@ManyToOne(() => Case, (c) => c.notes)` pointed at `Case.notes`, but that's a
   plain `text` column, not a relation — the actual `@OneToMany` relation on `Case`
   is named `caseNotes`. Fixed the inverse-side reference in `case-note.entity.ts`,
   fixed `cases.service.ts` `findOne()`'s `relations: [...]` array to request
   `caseNotes` instead of `'notes'`, and aliased `foundCase.notes = foundCase.caseNotes`
   before returning so `CaseResponseDto.notes` (declared as `CaseNoteResponseDto[]`)
   actually gets populated instead of silently returning `undefined`.
4. **`POST /api/cases/:id/assignments` and `/notes` always 404'd.** Neither
   controller method passed `user.tenantId` through to `casesService.findOne()`,
   which throws `NotFoundException('Tenant ID is required...')` whenever `tenantId`
   is falsy. Both services now accept `tenantId` and both controller methods pass
   `user.tenantId`.

**These are uncommitted local changes** (`git diff --stat`: 4 backend source files,
~59 insertions / 118 deletions of dead code) — review and commit them from the
backend repo before they're lost. Note `package-lock.json` also shows as modified
from an `npm install` run during this session — check that diff before committing.

## Frontend: signup form was missing `firmName`

`SignupDto.firmName` is required (by the backend's own doc comment, if not
strictly enforced) whenever `userType: LAWYER`. The frontend form never
collected it, so every lawyer signup silently got a low-quality auto-generated
tenant name (e.g. `"Firm Law Firm"` derived from the last name). Added a
conditional "اسم مكتب المحاماة" field to `src/pages/Signup.jsx`, shown only when
`userType === LAWYER`, and wired it into the signup payload.

## Response shapes are richer than the Swagger DTOs claim

The Swagger spec is aspirational in places — several controllers just return the
raw TypeORM entity/relations rather than transforming through the declared
`ResponseDto`, so what actually comes over the wire has more (and sometimes
differently-named) fields than documented:

- **`GET /api/cases`, `/finance/invoices`, `/hearings`, `/tasks` all embed their
  relations directly** — an invoice has `.client` (full `ClientResponseDto`-shaped
  object) and `.case` (full case object, so `.case.caseNumber` is right there);
  a hearing has `.case` and `.court`; a task has `.case` and `.assignee` (not
  `.employee` — different name than you'd guess). **Use these embedded objects
  instead of cross-referencing separate list calls** — it's both fewer requests
  and more reliable than joining client-side.
- **Numeric columns (`amount`, invoice/payment amounts) come back as strings**
  (`"15000.00"`, not `15000`) — this is TypeORM's default behavior for
  `decimal`/`numeric` columns. Always `Number(x)` before arithmetic — `0 + "15000.00"`
  string-concatenates to `"015000.00"` instead of adding, which is a very easy
  bug to ship silently (found and fixed in `Invoices.jsx`/`FinanceReports.jsx`).

## Known backend issues (not fixable from the frontend)

1. **`GET /api/public/lawyers` and `/specializations` are not actually public.**
   `PublicTenantsController` has `@ApiBearerAuth()` and no `@Public()` decorator, so the
   global JWT guard still rejects anonymous requests with `401`. Anyone who isn't logged
   in cannot browse the marketplace, which defeats its purpose. Fix: add `@Public()` to
   `src/modules/tenants/controllers/public-tenants.controller.ts`.
2. **`secretary`, `assistant`, `accountant` roles have zero permissions seeded.**
   `seed.ts` only assigns permissions to `admin` and `lawyer`. An employee onboarded
   with one of those `roleIds` will get `403 Forbidden` on everything. Needs a
   permission set per role in the seed (or an admin UI to assign them).
3. **`GET /api/public/lawyers` ignores query params** — there's no specialization
   filter server-side despite the frontend being able to send one; filtering has to
   happen client-side over the returned array.
4. No **audit-log** or **expenses** endpoints exist anywhere in the spec — those two
   frontend pages stay mock-only until/unless a module is added.

## Auth model

- JWT access token (short-lived) + refresh token. `POST /api/auth/refresh` takes
  `{ refreshToken }`.
- `roles` and `permissions` come back as **flat string arrays** on login/signup
  (e.g. `roles: ["lawyer"]`, `permissions: ["cases.create", "cases.read", ...]`),
  not objects. `GET /api/users/me` returns the richer nested shape (`roles: [{ id,
  name, displayNameEn, displayNameAr, permissions }]`, `tenant: { id, name }`).

**Real seeded roles** (`name` field — this is what `roles` arrays contain):

| name | displayNameAr | Scope |
|---|---|---|
| `admin` | مدير المنصة | Platform admin. Only `users.*` permissions — not meant to drive the firm app. |
| `lawyer` | محامي / مدير مكتب | **Firm Admin.** Gets every non-`users` permission (cases, clients, finance, settings, everything). This is the single "owner" role — there is no separate restricted "regular lawyer" role server-side. |
| `secretary` | سكرتير | Seeded but **no permissions assigned yet** (see issue #2). |
| `assistant` | مساعد قانوني | Same — no permissions assigned yet. |
| `accountant` | محاسب | Same — no permissions assigned yet. |
| `client` | عميل | Portal role, `tenant: null`. |

### Auth DTOs (exact field names — several differ from the old guess)

```
POST /api/auth/login          { email, password }
POST /api/auth/signup         { email, password, firstName, lastName, userType: 'CLIENT'|'LAWYER', firmName? }
                               firmName required when userType = LAWYER
POST /api/auth/refresh        { refreshToken }
POST /api/auth/logout         (bearer token, no body)
POST /api/auth/forgot-password { email }
POST /api/auth/reset-password  { token, newPassword }        // ⚠ was guessed as `password`
POST /api/auth/change-password { oldPassword, newPassword }   // ⚠ was guessed as `currentPassword`
```

All auth endpoints return `{ accessToken, refreshToken, user: { id, email, roles, permissions } }`
(login/signup) — call `GET /api/users/me` right after to get `firstName`/`lastName`/`tenant`.

## Resource schemas (fields the frontend must render)

### Cases — `CaseResponseDto`
```
id, title, caseNumber,
status: OPEN | IN_PROGRESS | CLOSED | ARCHIVED,
type: CIVIL | CRIMINAL | COMMERCIAL | LABOR | FAMILY | ADMINISTRATIVE,
clientId, client?: ClientResponseDto,
courtId, court?: CourtResponseDto,
filingDate, description,
assignments: [{ id, role: LEAD|SUPPORT, employee?: EmployeeResponseDto }],
notes: [{ id, content, createdAt }],
createdAt, updatedAt
```
No `priority` field, no direct `lawyer` field — the responsible lawyer is whichever
`assignments[].employee` has `role: 'LEAD'`.

### Clients — `ClientResponseDto`
```
id, type: INDIVIDUAL|COMPANY, name, email, phone, address, taxId, createdAt, updatedAt
```
No case count / balance on the object — compute client-side from the cases/invoices lists.

### Employees — `EmployeeResponseDto`
```
id, userId, position: <13-value enum>, department: <10-value enum>, hireDate,
createdAt, updatedAt, user: { id, email, firstName, lastName }
```
No phone, no status (active/suspended), no case count on this DTO.
Onboarding (`POST /api/employees/onboard`) needs `roleIds: string[]` (real role UUIDs
from `GET /api/roles`), `position`, `department`, `hireDate`, plus the usual credentials.

### Hearings — `HearingResponseDto`
```
id, caseId, courtId, date, status: SCHEDULED|COMPLETED|POSTPONED|CANCELLED, notes, createdAt, updatedAt
```
No client/judge/circuit/type fields — court and case are just IDs (not embedded), so
render a hearings table by cross-referencing the courts and cases lists client-side.

### Tasks — `TaskResponseDto`
```
id, title, description, status: TODO|IN_PROGRESS|DONE,
priority: LOW|MEDIUM|HIGH|URGENT, dueDate, caseId, assignedTo (employee id, no nested object),
createdAt, updatedAt
```
3 status columns, not 4.

### Documents — `DocumentResponseDto`
```
id, name, contentType, size (bytes), caseId, createdAt, updatedAt
```
No uploader, no category — derive the file-type badge from `contentType` (MIME), not extension.

### Courts — `CourtResponseDto`
```
id, name, type: FIRST_INSTANCE|APPEAL|SUPREME, location, contactInfo, createdAt, updatedAt
```

### Opponents — `OpponentResponseDto`
```
id, type: INDIVIDUAL|COMPANY, name, email, phone, address, notes, createdAt, updatedAt
```
No linkage back to cases in this DTO.

### Finance
```
InvoiceResponseDto: id, clientId, caseId, amount,
  status: DRAFT|ISSUED|PAID|CANCELLED, issueDate, dueDate, notes,
  payments: PaymentResponseDto[]   // sum these client-side for "paid"/"remaining"
PaymentResponseDto: id, invoiceId, amount, paymentDate,
  method: CASH|BANK_TRANSFER|CHEQUE|ONLINE, referenceNumber, createdAt
```

### Calendar
```
GET /api/calendar         -> EventResponseDto[]  (id, title, description, startTime, endTime,
                              type: MEETING|DEADLINE|CUSTOM, caseId, userId, createdAt, updatedAt)
GET /api/calendar/timeline -> mixed array, each item shaped:
  { id, itemType: 'CALENDAR_EVENT'|'HEARING'|'TASK', title, date, case?,
    // CALENDAR_EVENT also has: endDate, eventType
    // HEARING also has: status
    // TASK also has: status, priority }
  sorted by date ascending. This is the one to render the month grid from —
  it already merges events + hearings + tasks.
```

### Dashboard
```
GET /api/dashboard         -> DashboardSummaryDto
  { totalCases, activeCases, pendingTasks, upcomingHearings,
    totalInvoices, unpaidInvoices,
    recentActivity: [{ id, type, description, date }] }
GET /api/reports/dashboard -> DashboardMetricsDto (smaller, "my" stats only)
  { totalActiveCases, pendingTasks, upcomingHearings }
```
There is no monthly trend or case-type breakdown endpoint — don't fabricate one;
the dashboard KPIs and recent-activity feed come from `/api/dashboard`, and the
"today's hearings" mini table is built by fetching `/api/hearings` separately.

### Settings vs Tenant (firm info)
- `/api/settings` (+`/public`) is a generic key/value store (`{ key, value, description,
  isPublic }`) — keep this for arbitrary app settings.
- **Firm info now belongs to the Tenants module**, not generic settings:
  ```
  GET/PATCH /api/tenants/my-firm
    { id, name, subdomain, taxId, contactEmail, phone, address,
      specializations: string[], publicContactEmail, publicContactPhone,
      website, logoUrl }
  POST /api/tenants/my-firm/logo   (multipart upload)
  ```
  The Settings page's "معلومات المكتب" panel should read/write this, not `/api/settings`.

### Roles — `GET /api/roles`
```
[{ id, name, displayNameEn, displayNameAr, permissions? }]
GET /api/roles/permissions -> [{ id, resource, action, displayNameEn, displayNameAr }]
```

### Notifications — `NotificationResponseDto`
```
{ id, userId, title, message, isRead,
  type: HEARING_REMINDER|TASK_ASSIGNED|INVOICE_DUE|SYSTEM_ALERT, createdAt }
```
Unread count = `notifications.filter(n => !n.isRead).length`, not the array length.

### Public Marketplace — raw query result, NOT a documented DTO
`GET /api/public/lawyers` returns (per `TenantsService.findAllLawyersPublicly`, a raw
SQL projection — field names are whatever the `AS` aliases say):
```
[{ firmId, firmName, address, specializations: string[], publicContactEmail,
   publicContactPhone, website, lawyerId, firstName, lastName, avatarUrl,
   averageRating, reviewCount }]
```
`GET /api/public/lawyers/specializations` returns the specializations **dictionary**,
not a list: `{ CRIMINAL_LAW: { en, ar }, CORPORATE_LAW: { en, ar }, ... }` (14 keys).

### Reviews / Consultations
```
CreateReviewDto:       { lawyerId, rating (1-5), comment?, caseId? }
CreateConsultationDto: { lawyerId, tenantId, type: ONLINE|OFFICE|PHONE,
                          scheduledDate, duration (minutes), categoryId?, notes? }
```
`tenantId` for a marketplace row is that row's `firmId`.
